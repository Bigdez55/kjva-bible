# Corpus Workspace

Each consuming project drops its domain corpus into a subdirectory of `corpus/`,
named `<corpus-id>/`. The shipped substrate defaults to `domain_corpus_v1/`
across the training, evaluation, and export scripts; override with `--corpus`.

## Expected layout

```text
corpus/
├── <corpus-id>/
│   ├── corpus.txt              required — flat UTF-8 training text
│   ├── verses.jsonl            optional — one record per line, fields below
│   ├── byte_vocab.json         optional — exported alongside the model
│   ├── manifest.json           optional — corpus metadata
│   ├── retrieval_index.json    optional — used if the consuming project
│   │                            ships its own retrieval server
│   ├── validation_report.json  optional — produced by your validator
│   └── tokens_byte_uint16.npy  generated by train_byte.py on first run
└── programs/                   omni training program corpus
```

### `verses.jsonl` schema (optional)

The benchmark/eval scripts treat `verses.jsonl` as opt-in. If present, each
line is one JSON object. The benchmark recognises these fields:

- `text`        — required for any record used by the per-category / per-group
                  perplexity sections.
- `category`    — optional, enables `bench_canon_ppl` (per-category PPL).
- `group`       — optional, enables `bench_book_ppl` (per-group PPL).

Any additional fields the consuming project needs (book, chapter, citation,
etc.) are passed through and ignored by the substrate scripts.

## Building the corpus

The substrate intentionally does NOT ship a domain corpus builder — the
mapping from raw source documents to a clean `corpus.txt` is project-specific.
A consuming project adds its own builder under `scripts/` (or anywhere it
likes) and writes the produced files into `corpus/<corpus-id>/`.

## Subdirectories

- `<corpus-id>/` — your domain corpus + generated artifacts.
- `programs/`   — training-program corpus generated from the omni training
                  registry (`omni_training_programs.jsonl`).
